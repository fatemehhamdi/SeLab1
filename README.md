# Simple Chess

## معرفی پروژه

این پروژه یک بازی شطرنج ساده‌ی دونفره است که با React و Vite و بدون بک‌اند
پیاده‌سازی شده است. دو بازیکن می‌توانند روی یک صفحه‌ی مشترک بازی کنند و وضعیت
بازی در مرورگر مدیریت می‌شود.

## ویژگی‌های بازی

- نمایش صفحه‌ی شطرنج ۸×۸ با ۶۴ خانه
- قرارگیری مهره‌های سفید و سیاه در موقعیت اولیه
- انتخاب مهره‌ی بازیکنِ نوبت فعلی
- نمایش خانه‌های مجاز برای هر مهره
- پیاده‌سازی حرکت پایه‌ی سرباز، رخ، فیل، وزیر، اسب و شاه
- جلوگیری از خروج مهره از صفحه و عبور مهره‌های خطی از روی مهره‌های دیگر
- جابه‌جایی مهره به مقصد معتبر
- گرفتن مهره‌ی حریف و جلوگیری از گرفتن مهره‌ی خودی
- مدیریت نوبت سفید و سیاه
- نمایش پیام حرکت معتبر یا غیرمجاز
- نمایش تاریخچه‌ی حرکت‌ها شامل مبدأ و مقصد
- امکان شروع مجدد بازی و reset شدن صفحه، نوبت و تاریخچهı
- طراحی واکنش‌گرا برای دسکتاپ، تبلت و موبایل

این پروژه قوانین پیشرفته‌ی شطرنج مانند کیش، مات، قلعه، آن‌پاسان و ترفیع سرباز
را پوشش نمی‌دهد و هدف آن پیاده‌سازی یک بازی پایه‌ی آموزشی است.

## اجرای محلی

پیش‌نیازها:

`http://localhost:5173`، را در مرورگر باز کنید.

## GitHub Actions و استقرار

در پروژه دو فایل workflow وجود دارد:

### `.github/workflows/deploy.yml`

این workflow با push شدن تغییرات به شاخه‌ی `main` یا اجرای دستی فعال می‌شود.
jobهای آن عبارت‌اند از:

- `build`: دریافت کد، نصب Node.js و وابستگی‌ها، اجرای `npm run lint`، اجرای
  `npm run build` و آماده‌سازی پوشه‌ی `dist` به‌عنوان artifact مربوط به Pages.
- `deploy`: پس از موفقیت job `build`، artifact را با `actions/deploy-pages` روی
  GitHub Pages منتشر می‌کند.

### `.github/workflows/mirror-to-gitlab.yml`

این workflow با هر push، ایجاد یا حذف شاخه اجرا می‌شود. job `mirror` تاریخچه‌ی
کامل repository را دریافت می‌کند و با استفاده از secret به نام `GITLAB_TOKEN`
تغییرات را به GitLab mirror می‌کند.

برای فعال‌کردن انتشار، در GitHub باید از مسیر زیر منبع Pages روی GitHub Actions
تنظیم شود:

```text
Settings → Pages → Source: GitHub Actions
```

## ساختار شاخه‌ها و محدودیت شاخه‌ی main

شاخه‌های پروژه عبارت‌اند از:

- `main`: شاخه‌ی اصلی و پایدار پروژه
- `develop`: شاخه‌ی یکپارچه‌سازی و توسعه
- `feature`: شاخه‌ی توسعه‌ی قابلیت‌های جدید
- `hotfix`: شاخه‌ی رفع اشکال‌های فوری

برای محافظت از `main` در GitLab از **Branch rule** و در GitHub از **Rulesets**
استفاده شده است. این قوانین از تغییر مستقیم و push بدون کنترل به `main` جلوگیری
می‌کنند و تغییرات باید از مسیر مجاز تعریف‌شده، معمولاً Pull Request یا Merge
Request و بررسی آن، وارد شاخه‌ی اصلی شوند. بنابراین منظور فنی دقیق این نیست که
`main` فقط با هر push معمولی تغییر کند؛ بلکه push مستقیم محدود شده و ورود تغییرات
به شاخه‌ی اصلی تحت قوانین repository انجام می‌شود.

## گزارش commit و همکاری

برای مشاهده‌ی شاخه‌ها و تاریخچه:

```bash
git branch -a
git log --oneline --graph --decorate --all
```

برای مشاهده‌ی remoteها:

```bash
git remote -v
```

در این پروژه remote مربوط به GitHub با نام `origin` و remote مربوط به GitLab با
نام `gitlab` تعریف شده‌اند.

## نمونه‌ی همگام‌سازی و حل تعارض

در یکی از مراحل، به‌دلیل fetch نکردن تغییرات جدید remote، نسخه‌ی محلی با نسخه‌ی
remote همگام نبود و هنگام ترکیب تغییرات conflict ایجاد شد. در VS Code برای حل
این conflict گزینه‌ی `Choose Both Changes` انتخاب شد؛ سپس فایل بررسی و ذخیره،
و تغییر نهایی stage و commit شد.

این مورد به‌عنوان ادامه‌ی مشکل conflict قبلی پروژه نیز ثبت شد: علت اصلی،
به‌روز نبودن نسخه‌ی محلی نسبت به remote بود و با دریافت تغییرات و انتخاب
`Choose Both Changes` در فایل مربوط، تعارض برطرف شد.

برای دریافت تغییرات remote و به‌روزکردن شاخه‌ی محلی می‌توان از دستور زیر استفاده
کرد:

```bash
git fetch origin
git pull --rebase origin main
```

`git pull --rebase origin main` تغییرات `origin/main` را دریافت و commitهای
محلی را روی آخرین وضعیت remote دوباره اعمال می‌کند. پس از حل conflict و پایان
موفق rebase، تغییرات با دستور زیر به remote ارسال می‌شوند:

```bash
git add <file>
git rebase --continue
git push origin main
```

اگر conflict در یک merge معمولی رخ دهد، پس از انتخاب تغییرات صحیح می‌توان از
دستورهای زیر استفاده کرد:

```bash
git status
git add <file>
git commit
```

## پرسش‌های نظری Git

### پوشه‌ی `.git` چیست و با چه دستوری ساخته می‌شود؟

پوشه‌ی `.git` هسته‌ی repository محلی Git است. در آن objectهای commit، tree و
blob، referenceهای branch و tag، اطلاعات HEAD، تنظیمات repository، index و
reflog نگهداری می‌شود. این پوشه معمولاً با دستور زیر ساخته می‌شود:

```bash
git init
```

در صورتی که repository از remote دریافت شود، دستور `git clone` نیز یک پوشه‌ی
`.git` ایجاد می‌کند.

### atomic بودن در Atomic Commit و Atomic Pull Request یعنی چه؟

Atomic یعنی یک عملیات باید یک واحد منطقی و کامل باشد و یا به‌طور کامل انجام شود
یا اصلاً انجام نشود.

- **Atomic commit** فقط یک تغییر منطقی مرتبط را ثبت می‌کند؛ بنابراین commit
  کامل، قابل‌فهم و مستقل است و نباید نصفه یا ترکیبی از چند موضوع نامرتبط باشد.
- **Atomic pull request** یک قابلیت یا تغییر منطقی مشخص را ارائه می‌کند و
  نباید چند تغییر مستقل و نامرتبط را در یک Pull Request مخلوط کند. در نتیجه
  بررسی، تست و rollback آن ساده‌تر است.

### تفاوت `fetch`، `pull`، `merge`، `rebase` و `cherry-pick`

- `git fetch`: commitها و referenceهای جدید remote را دریافت می‌کند، اما شاخه‌ی
  فعلی و فایل‌های working tree را تغییر نمی‌دهد.
- `git pull`: معمولاً `fetch` و سپس `merge` را اجرا می‌کند؛ با گزینه‌ی `--rebase`
  می‌تواند commitهای محلی را روی آخرین commit remote بازپخش کند.
- `git merge`: تاریخچه‌ی دو شاخه را ترکیب می‌کند و در صورت نیاز merge commit
  می‌سازد.
- `git rebase`: commitهای یک شاخه را روی پایه‌ی جدید دوباره اعمال می‌کند و
  معمولاً تاریخچه‌ای خطی‌تر می‌سازد. rebase شناسه‌ی commitهای بازپخش‌شده را
  تغییر می‌دهد.
- `git cherry-pick`: یک یا چند commit مشخص را بدون ادغام کل شاخه روی شاخه‌ی
  فعلی اعمال می‌کند.

### تفاوت `reset`، `revert`، `restore`، `switch` و `checkout`

- `git reset`: اشاره‌گر branch و معمولاً HEAD را به commit دیگری منتقل می‌کند.
  بسته به گزینه (`--soft`، `--mixed` یا `--hard`) stage و working tree نیز
  تغییر می‌کنند؛ بنابراین ممکن است تاریخچه‌ی محلی را بازنویسی کند.
- `git revert`: برای یک commit قبلی، commit معکوس جدید می‌سازد و روش امن‌تری
  برای برگرداندن تغییرات منتشرشده است.
- `git restore`: فایل‌ها را از index یا یک commit بازیابی می‌کند و برای کنار
  گذاشتن تغییرات working tree یا خارج‌کردن فایل از stage استفاده می‌شود.
- `git switch`: دستور جدیدتر و اختصاصی برای جابه‌جایی یا ساخت branch است.
- `git checkout`: دستور قدیمی‌تر و چندمنظوره‌ای است که هم برای جابه‌جایی branch
  و هم بازیابی فایل استفاده می‌شد؛ معمولاً `switch` و `restore` جایگزین‌های
  واضح‌تر آن هستند.

### Stage یا Index چیست و `stash` چه کاری انجام می‌دهد؟

Stage یا همان index ناحیه‌ای بین working tree و commit است. با `git add` مشخص
می‌کنیم کدام تغییرات باید در commit بعدی قرار بگیرند.

`git stash` تغییرات موقت commit‌نشده، شامل تغییرات staged و unstaged، را کنار
می‌گذارد و working tree را تمیز می‌کند تا بتوان branch را عوض کرد یا تغییرات
remote را دریافت کرد. تغییرات بعداً با `git stash pop` یا `git stash apply`
قابل بازگردانی هستند.

### Snapshot چیست و چه ارتباطی با commit دارد؟

Snapshot تصویری از وضعیت فایل‌های پروژه در یک لحظه‌ی مشخص است. در Git، commit
بیشتر شبیه ثبت snapshot کامل ساختار پروژه است تا ذخیره‌ی صرفاً یک diff. Git برای
فایل‌هایی که نسبت به snapshot قبلی تغییر نکرده‌اند، object جدید تکراری ذخیره
نمی‌کند و از object قبلی استفاده می‌کند؛ به همین دلیل commitها مستقل و قابل
بازیابی هستند، هرچند Git هنگام نمایش history می‌تواند تفاوت بین snapshotها را
محاسبه کند.

مطالعه‌ی بیشتر:

[Commits are snapshots, not diffs](https://github.blog/open-source/git/commits-are-snapshots-not-diffs/)

### تفاوت Local Repository و Remote Repository چیست؟

- **Local repository** نسخه‌ای از پروژه و تاریخچه‌ی Git است که روی سیستم
  توسعه‌دهنده قرار دارد و commitها در آن به‌صورت محلی ساخته و بررسی می‌شوند.
- **Remote repository** نسخه‌ای از repository روی سرویس‌هایی مانند GitHub یا
  GitLab است که برای اشتراک‌گذاری، همکاری، backup و اجرای CI/CD استفاده می‌شود.

با `commit` تغییرات در local ثبت می‌شوند و با `push` به remote ارسال می‌شوند.
برای دریافت تغییرات remote نیز می‌توان از `fetch`، `pull` یا ترکیب مناسب آن‌ها
استفاده کرد.

## مدیریت کارها با Issue و Kanban Board

برای مدیریت روند انجام کارها از Issueها و Kanban Board استفاده شده است. هر Issue
در سطح کلی می‌تواند یکی از دو وضعیت زیر را داشته باشد:

- `Open`: Issue هنوز باز است و کار مربوط به آن تکمیل نشده یا در حال پیگیری است.
- `Closed`: کار Issue تکمیل شده و Issue بسته شده است.

علاوه بر وضعیت باز یا بسته‌بودن Issue، کارت‌ها در Kanban Board بین ستون‌های زیر
حرکت می‌کنند:

- `To Do`: کارهایی که تعریف شده‌اند اما هنوز شروع نشده‌اند.
- `In Progress`: کارهایی که در حال پیاده‌سازی یا بررسی هستند.
- `Done`: کارهایی که تکمیل و بررسی شده‌اند.

به این ترتیب، `Open` و `Closed` وضعیت کلی Issue را نشان می‌دهند و `To Do`,
`In Progress` و `Done` مرحله‌ی پیشرفت کارت در Kanban Board را مشخص می‌کنند.
