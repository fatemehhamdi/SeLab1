# Simple Chess

## معرفی پروژه

این پروژه یک بازی شطرنج ساده‌ی دونفره است که با React و Vite و بدون بک‌اند
پیاده‌سازی شده است. دو بازیکن می‌توانند روی یک صفحه‌ی مشترک بازی کنند و وضعیت
بازی در مرورگر مدیریت می‌شود.

## ویژگی‌های بازی

- نمایش صفحه‌ی شطرنج ۸×۸ با ۶۴ خانه
- قرارگیری مهره‌های سفید و سیاه در موقعیت اولیه
- انتخاب مهره‌ی بازیکنِ نوبت فعلی
- نمایش خانه‌های مجاز برای هر مهره
- پیاده‌سازی حرکت پایه‌ی سرباز، رخ، فیل، وزیر، اسب و شاه
- جلوگیری از خروج مهره از صفحه و عبور مهره‌های خطی از روی مهره‌های دیگر
- جابه‌جایی مهره به مقصد معتبر
- گرفتن مهره‌ی حریف و جلوگیری از گرفتن مهره‌ی خودی
- مدیریت نوبت سفید و سیاه
- نمایش پیام حرکت معتبر یا غیرمجاز
- نمایش تاریخچه‌ی حرکت‌ها شامل مبدأ و مقصد
- امکان شروع مجدد بازی و reset شدن صفحه، نوبت و تاریخچهı
- طراحی واکنش‌گرا برای دسکتاپ، تبلت و موبایل

این پروژه قوانین پیشرفته‌ی شطرنج مانند کیش، مات، قلعه، آن‌پاسان و ترفیع سرباز
را پوشش نمی‌دهد و هدف آن پیاده‌سازی یک بازی پایه‌ی آموزشی است.

## GitHub Actions و استقرار

در پروژه دو فایل workflow وجود دارد:

### `.github/workflows/deploy.yml`

این workflow با push شدن تغییرات به شاخه‌ی `main` یا اجرای دستی فعال می‌شود.
jobهای آن عبارت‌اند از:

- `build`: دریافت کد، نصب Node.js و وابستگی‌ها، اجرای `npm run lint`، اجرای
  `npm run build` و آماده‌سازی پوشه‌ی `dist` به‌عنوان artifact مربوط به Pages.
- `deploy`: پس از موفقیت job `build`، artifact را با `actions/deploy-pages` روی
  GitHub Pages منتشر می‌کند.

### `.github/workflows/mirror-to-gitlab.yml`

این workflow با هر push، ایجاد یا حذف شاخه اجرا می‌شود. job `mirror` تاریخچه‌ی
کامل repository را دریافت می‌کند و با استفاده از secret به نام `GITLAB_TOKEN`
تغییرات را به GitLab mirror می‌کند.

برای فعال‌کردن انتشار، در GitHub باید از مسیر زیر منبع Pages روی GitHub Actions
تنظیم شود:

```text
Settings → Pages → Source: GitHub Actions
```

## ساختار شاخه‌ها و محدودیت شاخه‌ی main

شاخه‌های پروژه عبارت‌اند از:

- `main`: شاخه‌ی اصلی و پایدار پروژه
- `develop`: شاخه‌ی یکپارچه‌سازی و توسعه
- `feature`: شاخه‌ی توسعه‌ی قابلیت‌های جدید
- `hotfix`: شاخه‌ی رفع اشکال‌های فوری

برای محافظت از `main` در GitLab از **Branch rule** و در GitHub از **Rulesets**
استفاده شده است. این قوانین از تغییر مستقیم و push بدون کنترل به `main` جلوگیری
می‌کنند و تغییرات باید از مسیر مجاز تعریف‌شده، معمولاً Pull Request یا Merge
Request و بررسی آن، وارد شاخه‌ی اصلی شوند. بنابراین منظور فنی دقیق این نیست که
`main` فقط با هر push معمولی تغییر کند؛ بلکه push مستقیم محدود شده و ورود تغییرات
به شاخه‌ی اصلی تحت قوانین repository انجام می‌شود.

## گزارش commit و همکاری

برای مشاهده‌ی شاخه‌ها و تاریخچه:

```bash
git branch -a
git log --oneline --graph --decorate --all
```

برای مشاهده‌ی remoteها:

```bash
git remote -v
```

در این پروژه remote مربوط به GitHub با نام `origin` و remote مربوط به GitLab با
نام `gitlab` تعریف شده‌اند.

## نمونه‌ی همگام‌سازی و حل تعارض

در یکی از مراحل، به‌دلیل fetch نکردن تغییرات جدید remote، نسخه‌ی محلی با نسخه‌ی
remote همگام نبود و هنگام ترکیب تغییرات conflict ایجاد شد. در VS Code برای حل
این conflict گزینه‌ی `Choose Both Changes` انتخاب شد؛ سپس فایل بررسی و ذخیره،
و تغییر نهایی stage و commit شد.

این مورد به‌عنوان ادامه‌ی مشکل conflict قبلی پروژه نیز ثبت شد: علت اصلی،
به‌روز نبودن نسخه‌ی محلی نسبت به remote بود و با دریافت تغییرات و انتخاب
`Choose Both Changes` در فایل مربوط، تعارض برطرف شد.

برای دریافت تغییرات remote و به‌روزکردن شاخه‌ی محلی می‌توان از دستور زیر استفاده
کرد:

```bash
git fetch origin
git pull --rebase origin main
```

`git pull --rebase origin main` تغییرات `origin/main` را دریافت و commitهای
محلی را روی آخرین وضعیت remote دوباره اعمال می‌کند. پس از حل conflict و پایان
موفق rebase، تغییرات با دستور زیر به remote ارسال می‌شوند:

```bash
git add <file>
git rebase --continue
git push origin main
```

اگر conflict در یک merge معمولی رخ دهد، پس از انتخاب تغییرات صحیح می‌توان از
دستورهای زیر استفاده کرد:

```bash
git status
git add <file>
git commit
```


# پرسش‌های نظری Git

### ۱. پوشه‌ی `.git` چیست؟ چه اطلاعاتی در آن ذخیره می‌شود؟ با چه دستوری ساخته می‌شود؟
پوشه‌ی `.git` یک پوشه‌ی مخفی در ریشه‌ی هر repository است و در واقع «خودِ» ریپازیتوری محلی محسوب می‌شود؛ هر چیزی که Git برای نگه‌داری تاریخچه، شاخه‌ها و تنظیمات نیاز دارد داخل همین پوشه است، نه در فایل‌های خود پروژه.

اطلاعات اصلی داخل آن:
- `objects/` — دیتابیس آبجکت‌های Git: `blob` (محتوای فایل)، `tree` (ساختار پوشه)، `commit` (اطلاعات هر کامیت)، `tag`
- `refs/` — اشاره‌گر به کامیت‌ها؛ شاخه‌ها در `refs/heads`، تگ‌ها در `refs/tags`، شاخه‌های ریموت در `refs/remotes`
- `HEAD` — اشاره‌گر به شاخه یا کامیتی که الان روی آن هستیم
- `index` — همان staging area (فهرست تغییرات آماده برای کامیت بعدی)
- `config` — تنظیمات محلیِ همین ریپو (remote، تنظیمات کاربر و ...)
- `logs/` — تاریخچه‌ی جابه‌جایی HEAD و شاخه‌ها (reflog)
- `hooks/` — اسکریپت‌هایی که موقع رویدادهای گیت (قبل/بعد از commit، push و ...) اجرا می‌شوند

با دستور `git init` ساخته می‌شود؛ همچنین هنگام `git clone` هم به‌صورت خودکار ساخته و پر می‌شود.

### ۲. منظور از atomic بودن در atomic commit و atomic pull-request چیست؟
Atomic یعنی «تجزیه‌ناپذیر» — هر واحد کاری فقط یک تغییرِ کامل و مستقل را در بر بگیرد، نه چند کارِ نامرتبط قاطی‌شده با هم.

- **Atomic commit**: هر کامیت فقط یک تغییر منطقی انجام می‌دهد (مثلاً فقط رفع یک باگ یا فقط اضافه‌کردن یک قابلیت). فایده‌اش این است که می‌توان آن را جدا از بقیه revert یا cherry-pick کرد، تاریخچه خواناتر می‌شود و code review راحت‌تر انجام می‌گیرد.
- **Atomic pull request**: یک PR هم باید یک تغییر کامل و مستقل را پیاده کند، نه چند موضوع نامرتبط با هم؛ این باعث می‌شود review سریع‌تر و دقیق‌تر انجام شود، تست‌پذیری بهتری داشته باشد و در صورت نیاز، کل PR بدون تأثیر روی بقیه‌ی کدها قابل revert باشد.

### ۳. تفاوت دستورهای fetch، pull، merge، rebase و cherry-pick
- `git fetch`: کامیت‌ها/شاخه‌ها/تگ‌های جدید را از remote می‌گیرد و در شاخه‌های ردیابی ریموت (مثل `origin/main`) ذخیره می‌کند، اما هیچ تغییری در working directory یا شاخه‌ی محلی فعلی ایجاد نمی‌کند.
- `git pull`: معادل `git fetch` + `git merge` است (یا با فلگ `--rebase`، معادل `fetch` + `rebase`)؛ یعنی هم می‌گیرد و هم شاخه‌ی فعلی را با آن آپدیت می‌کند.
- `git merge`: تاریخچه‌ی دو شاخه را ترکیب می‌کند؛ اگر fast-forward نباشد، یک «merge commit» با دو پدر می‌سازد و کل تاریخچه‌ی هر دو شاخه حفظ می‌شود.
- `git rebase`: کامیت‌های یک شاخه را برمی‌دارد و روی نوکِ شاخه‌ی دیگر بازپخش می‌کند؛ کامیت‌های جدیدی با هش جدید ساخته می‌شود و تاریخچه خطی (بدون merge commit) می‌شود.
- `git cherry-pick`: فقط یک کامیت مشخص (با هش آن) را از یک شاخه برمی‌دارد و روی شاخه‌ی فعلی اعمال می‌کند، بدون اینکه کل شاخه merge یا rebase شود.

### ۴. تفاوت دستورهای reset، revert، restore، switch و checkout
- `git reset`: اشاره‌گر شاخه (HEAD) را به کامیت دیگری منتقل می‌کند؛ بسته به حالت، روی staging و working directory هم اثر می‌گذارد:
  - `--soft`: فقط HEAD جابه‌جا می‌شود.
  - `--mixed` (پیش‌فرض): HEAD و staging جابه‌جا می‌شود، فایل‌های working directory دست‌نخورده می‌ماند.
  - `--hard`: HEAD، staging و working directory همه به آن کامیت برمی‌گردد (تغییرات از دست می‌رود).
  تاریخچه را بازنویسی می‌کند؛ روی شاخه‌های مشترک/push‌شده خطرناک است.
- `git revert`: یک کامیت جدید می‌سازد که اثر یک کامیت قبلی را خنثی می‌کند؛ تاریخچه را بازنویسی نمی‌کند، پس برای شاخه‌های عمومی و مشترک امن است.
- `git restore`: فایل‌ها را در working directory یا staging area به حالت مشخصی برمی‌گرداند (مثلاً discard کردن تغییرات محلی یا unstage کردن یک فایل).
- `git switch`: فقط برای جابه‌جایی بین شاخه‌ها استفاده می‌شود.
- `git checkout`: دستور قدیمی‌تر و چندمنظوره که هم می‌توانست شاخه عوض کند، هم فایل restore کند، هم روی یک کامیت خاص برود (detached HEAD)؛ چون چندکاره و گاهی گیج‌کننده بود، Git از نسخه‌ی ۲.۲۳ به بعد `switch` و `restore` را برای تفکیک همین وظایف معرفی کرد.

### ۵. منظور از stage (index) چیست؟ دستور stash چه کاری انجام می‌دهد؟
- **stage / index**: ناحیه‌ای میانی بین working directory و مخزن (`.git`) است. وقتی با `git add` فایلی را stage می‌کنید، یعنی آن را برای قرارگرفتن در کامیت بعدی «آماده» کرده‌اید. عملاً index همان پیش‌نمایشِ snapshotی است که در کامیت بعدی ثبت خواهد شد.
- **`git stash`**: تغییرات ثبت‌نشده (چه staged و چه unstaged) را موقتاً در یک استک ذخیره می‌کند و working directory را تمیز و مطابق آخرین کامیت می‌کند؛ برای وقتی مفید است که بدون کامیت‌کردن نیاز دارید سریع شاخه عوض کنید یا کار دیگری انجام دهید. بعداً با `git stash pop` (اعمال و حذف از استک) یا `git stash apply` (فقط اعمال، بدون حذف) می‌توان تغییرات را برگرداند.

### ۶. مفهوم snapshot به چه معناست؟ ارتباط آن با commit چیست؟
برخلاف سیستم‌های کنترل نسخه‌ی قدیمی‌تر مثل SVN که فقط تفاوت (diff) بین نسخه‌ها را ذخیره می‌کنند، Git در هر commit یک **snapshot**، یعنی «عکسِ کاملِ» تمام فایل‌های پروژه در همان لحظه، ذخیره می‌کند نه فقط تفاوت‌ها.

برای بهینه بودن، اگر فایلی نسبت به کامیت قبلی تغییر نکرده باشد، Git دوباره آن را ذخیره نمی‌کند و فقط به همان blob قبلی اشاره (reference) می‌دهد؛ پس با اینکه مفهومش «snapshot کامل» است، از نظر فضای ذخیره‌سازی بسیار بهینه عمل می‌کند.

هر آبجکت commit شامل این‌هاست: اشاره‌گر به یک آبجکت tree (که ساختار کامل پوشه‌ها/فایل‌ها، یعنی همان snapshot را نشان می‌دهد)، اشاره‌گر به کامیتِ (های) والد، اطلاعات نویسنده، پیام کامیت و timestamp. یعنی commit = متادیتا + پوینتر به یک snapshot از کل پروژه در آن لحظه.
(منبع پیشنهادی: فصل «Git Basics – Snapshots, Not Differences» در کتاب Pro Git — git-scm.com/book)

### ۷. تفاوت‌های local repository و remote repository
- **Local repository**: همان پوشه‌ی `.git` روی سیستم خودتان است؛ کل تاریخچه، شاخه‌ها و آبجکت‌ها را به‌طور کامل دارد و می‌توانید کاملاً آفلاین commit، branch، merge و ... انجام دهید.
- **Remote repository**: نسخه‌ای از همان ریپازیتوری است که جای دیگری (مثلاً روی GitHub، GitLab یا سرور تیم) میزبانی می‌شود و نقطه‌ی مرجع مشترک برای همکاری تیمی است؛ معمولاً به‌صورت «bare repository» است (بدون working directory). ارتباط بین local و remote از طریق دستورهایی مثل `fetch`، `pull` و `push` برقرار می‌شود.
